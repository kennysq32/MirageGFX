Mirage GFX v1 Spec

A display-list graphics protocol between an ESP32-S3 geometry engine and a Tang Nano 9K raster/display controller, targeting a skinned, textured character at 480×640 RGB565, 60 fps.

host ESP32-S3 raster GW1NR-9 (Tang Nano 9K) panel 480×640 RGB565 DPI budget ≤6k tris @ 60 fps

2System dataflow

3Link & sideband

The ESP32-S3's esp_lcd i80 bus drives the FPGA as if it were a dumb display controller: 16 data lines + WR strobe + CS, DMA-fed from a command buffer built each frame. The FPGA captures words on WR edges into an asynchronous FIFO that crosses into the core clock domain. Run the bus at 10 MHz for bring-up, 20 MHz once signal integrity is verified (short wires, series resistors ≈ 33 Ω).

Sideband (FPGA → ESP32, 2 GPIOs)

SignalMeaningHost usage
VSYNCPulses at start of vertical blanking; also the moment SWAP takes effectFrame pacing: start building frame N+1 on the edge
BUSYCommand FIFO almost-full (≤ 64 words free)DMA pause / poll before large transfers. Sized so the in-flight DMA burst never overflows the FIFO

4Command protocol

The stream is a sequence of 16-bit words. Each command begins with a header word — opcode in the high byte, a small immediate argument in the low byte — followed by a fixed- or count-determined payload. Unknown opcodes are fatal in v1 (decoder asserts an error flag readable via a debug pin); there is no resync mechanism, so the host owns framing.

OpNamePayload (16-bit words)Semantics
0x00NOP—Padding / alignment
0x01CLEAR_RECTx0 y0 x1 y1 colorFill inclusive rect in the back buffer with RGB565 color. Host sends the union of last + current frame character bounds
0x02SET_PALETTEoffset count rgb565×countWrite entries into the 256-entry BSRAM palette
0x03TEX_UPLOADaddr_hi addr_lo len_hi len_lo data…Write 8bpp texels (2 per word) into the PSRAM texture region. Load-time only; texture layout is 8×4 tiled (§7)
0x04VTX_LOADbase count (vertex×4)×countLoad post-transform vertices into vertex RAM starting at index base (0–4095)
0x05DRAW_TRIScount (i0 i1 i2)×countRasterize indexed triangles in stream order — host has already sorted back-to-front. Indices reference vertex RAM
0x06SET_STATEarg byte in headerbit0 = texturing enable · bit1 = Gouraud modulate enable (off = texel only) · bit2 = flat fill (ignore texture, use vertex 0 color)
0x07SWAP—Request buffer swap; scanout latches the new front-buffer address at the next vsync. Draw commands after SWAP target the new back buffer

Note — no Z anywhere Because hidden surfaces are resolved by host-side sorting, the vertex carries no depth, the FPGA interpolates no depth, and no depth memory exists. This is the single biggest saver of LUTs and PSRAM bandwidth in the design.

Rasterizer

Edge-function (Pineda) rasterizer over the triangle's bounding box: setup computes three edge equations plus five interpolant gradients (U, V, R, G, B) using the GW1NR-9's DSP macros, then the walk phase steps one pixel per core clock, accumulating interpolants with adds only. Per pixel: three edge signs decide coverage → texel-cache lookup (8bpp) → palette to RGB565 → modulate with interpolated color (three small DSP multiplies) → into the burst write combiner, which coalesces scanline runs into PSRAM bursts. Top-left fill rule so shared edges never double-draw or gap — with back-to-front blending-free rendering this only matters for cracks, but cracks are visible.

7Texture path

Texels are stored in 8×4 tiles (32 bytes = one cache line = one efficient PSRAM burst) rather than row-major, so a cache miss pulls in a 2-D neighborhood instead of a 1-D strip — this is what makes the hit rate survive triangles that walk the texture diagonally. Address of texel (u,v): tile index (v»2)·32 + (u»3), byte within tile (v&3)·8 + (u&7). The host-side asset pipeline (a small Python script in the repo) does palette quantization to 256 colors and the tile swizzle offline; the ESP32 uploads the finished blob at boot with TEX_UPLOAD + SET_PALETTE.

Measure, don't assume The texel cache carries a hit/miss perf counter from day one. Expected hit rate on character UVs is > 90%; if measured lower, first suspects are UV seams in the mesh and tile size mismatch with typical triangle size.

9ESP32-S3 frame loop

on VSYNC edge:                          // 16.7 ms budget
  advance animation clock; evaluate bone matrices     (~0.2 ms)
  skin vertices  — 2 influences, fixed-point,
                   PIE SIMD if float is too slow      (~0.3–1.0 ms)
  transform to screen space, guard-band clip,
  back-face cull (~halves triangle count), light      (~0.8 ms)
  bucket-sort surviving tris by view depth
    (ordering table, 1024 buckets, O(n))              (~0.4 ms)
  compute dirty rect = union(prev bbox, cur bbox)
  emit stream: CLEAR_RECT · VTX_LOAD · SET_STATE
               · DRAW_TRIS (sorted) · SWAP
  start i80 DMA (overlaps with next frame's CPU work) (~4 ms wire time)

Total CPU ≈ 2–3 ms of a 16.7 ms frame on one core — enough headroom that game logic, IK, or a second character fits later. Core 0 stays free for the app; core 1 owns the render loop. Note the pipeline is one frame deep: the frame built now displays at the vsync after next.
